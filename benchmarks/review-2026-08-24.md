# Benchmarking review — 2026-08-24

A point-in-time assessment of the benchmark harness: what it measures well, what
is missing, and what order to add the missing pieces in relative to continuous
batching.

Reviewed: `benchmarks/bench_throughput.py`, `benchmarks/workloads.py`,
`benchmarks/sweep.py`, `benchmarks/hardware.py`, the batching path in
`src/tiny_llm_serve/engine/llm_engine.py`, and the committed sweep
`benchmarks/results/qwen3-8b-bfloat16-n512-seed0-cuda/`.

## What's already good

The measurement discipline is above average for a project this size: fresh
process per trial, OOM-as-a-result, resumable sweeps, git commit + dirty flag +
environment in every record, prefill/decode split, MBU against a real vendor
peak table, forced output lengths so token counts are byte-identical across
modes. Rules 1–4 in the README are the right rules.

So the gaps below aren't hygiene — they're about *what is being measured*, not
how carefully.

## Three gaps visible in the committed data

### 1. `kv_efficiency` under-indicts static batching by ~3x

It's the metric the README calls "the number that indicts it," but it's diluted
by prompt tokens, which are always fully used. Computed from the generators in
`benchmarks/workloads.py` at seed 0, n=512:

| workload | bs | `kv_efficiency` (recorded) | decode slot-step utilization | prefill pad utilization |
|---|---|---|---|---|
| mixed-out | 128 | 0.598 | **0.197** | 1.000 |
| sharegpt-like | 128 | 0.185 | **0.186** | **0.184** |
| uniform-512x128 | 128 | 1.000 | 1.000 | 1.000 |

On mixed-out at bs=128, 80% of decode slot-steps are idle sequences being
stepped and discarded. `kv_efficiency` reports 0.6; the real waste is 5.08x.

That ratio *is* continuous batching's headroom, and there is currently no metric
that states it. Add it **before** implementing CB — it turns "CB should help"
into a falsifiable prediction:

> mixed-out ≈5.1x, sharegpt-like ≈5.4x, uniform-512x128 ≈1.0x at bs=128.

Full table of the ideal (tail-waste-free) speedup, seed 0, n=512:

| workload | bs=8 | bs=32 | bs=128 | bs=256 |
|---|---|---|---|---|
| uniform-512x128 | 1.00x | 1.00x | 1.00x | 1.00x |
| mixed-out | 2.78x | 4.52x | 5.08x | 5.08x |
| sharegpt-like | 2.82x | 4.50x | 5.36x | 5.36x |

### 2. Prefill padding waste is entirely unmeasured

`generate_batch_ids` pads to `max(prompt_lens)`
(`src/tiny_llm_serve/engine/llm_engine.py:148`). On sharegpt-like that means
**82% of prefill FLOPs are spent on padding**. `prefill_time_s` is recorded but
nothing normalizes it, so there is no MFU to sit beside MBU.

This is the motivation for ragged/chunked prefill, and right now it's invisible.

### 3. MBU is flat at ~0.20 across the entire sweep

bs=1 through bs=256, all three workloads. That's the loudest number in the
dataset and the README doesn't mention it. Two readings, and the harness cannot
currently tell them apart:

- the engine achieves 20% of peak bandwidth, or
- the engine actually moves ~5x more bytes than `decode_bytes_read` (a *lower
  bound*) accounts for — attention score materialization, unfused
  RMSNorm/SwiGLU/RoPE activation traffic.

Worth resolving, because if there is a flat 5x implementation tax, it will
compress every batching win measured on top of it.

### Minor but load-bearing

- **No warmup and no repeats** — one trial per grid point, no spread. The README
  reads `s_per_decode_step` trends at a few percent resolution, which single
  unwarmed trials can't support.
- **`--sequential` was never run** in the committed sweep, so the naive-cache
  floor isn't on record; static bs=1 is standing in for it.
- **No per-request records** — one aggregate per trial, no timestamps. This is
  the single blocker for every latency metric below.

## Does offline-only force offline workloads?

Two independent axes are being conflated, and separating them is what unblocks
the rest:

- **Arrival process** — is the workload a *set* (all present at t=0) or a
  *trace* (timestamped)?
- **Admission model** — can the engine accept a request while others are in
  flight?

Today the engine can't admit mid-flight, so the *only* thing it could do with a
timestamped trace is buffer arrivals into waves. But that's not nothing —
"static batching served behind a queue" is a legitimate and important baseline.
It just requires a scheduler loop, which is most of the CB refactor anyway.

So: offline sets are the right call *today*, but the constraint is the missing
scheduler, not something intrinsic about offline benchmarking.

### On Poisson specifically

- **Open-loop vs closed-loop matters more than the distribution.** Closed-loop
  (N clients, each sends the next after its previous completes) is
  self-limiting — the queue can't explode, so the saturation knee never appears.
  Open-loop at fixed rate λ is what's needed, and it's what vLLM's
  `benchmark_serving.py` does.
- **Poisson is the right default, but parameterize it as gamma with a CV knob.**
  CV=1 recovers Poisson exactly; CV>1 gives burstiness. Real LLM traffic (Azure
  inference traces, BurstGPT) is markedly burstier than Poisson, and burstiness
  is precisely what CB absorbs and static batching cannot. One extra parameter,
  and it subsumes the standard.
- **The offline drain is already the λ→∞ end of that sweep.** It isn't being
  replaced — the rest of the x-axis is being added. Offline stays the correct
  measurement for capacity and the memory ceiling.

## Is latency meaningless offline?

No. What's missing offline is **queueing delay caused by arrivals**. Everything
caused by *the engine's own scheduling* is real, present, and currently
unmeasured:

- **TPOT is fully meaningful offline.** It's `s_per_decode_step`, already
  recorded. At mixed-out bs=256 it's 68 ms → **~14.7 tok/s per stream**, well
  under reading speed. That's a genuine SLO violation sitting in a committed
  record. The classic throughput-vs-per-stream-TPOT tradeoff curve is plottable
  from existing data, with no arrival process at all.
- **Head-of-line blocking is real offline.** Under `run_static`, a request in
  wave 5 waits for waves 1–4 to fully drain — queueing *without* an arrival
  process. On mixed-out the wave is held by its longest sequence. Per-request
  E2E measured from workload start would show it immediately.
- **TTFT offline is the weakest of the three** — roughly prefill time plus
  wave-wait, with no admission delay. Not meaningless, but it's the one that
  genuinely needs arrivals to be interesting.
- **For truly offline use cases** (eval harnesses, synthetic data generation,
  batch scoring) makespan *is* the metric and per-request latency legitimately
  doesn't matter. Don't drop it.

The blocker isn't offline-ness — it's that records carry no per-request
timestamps.

## Should online workloads come before continuous batching?

Partly. **Don't build the full online harness as a separate blocking project** —
it needs the same scheduler refactor CB needs. Split it three ways.

### Before CB — cheap, and it's the "before" picture that's otherwise lost

1. **Per-request timing in the offline harness** — arrival index, wave, prefill
   start/end, first token, completion. Emit TTFT/TPOT/E2E distributions relative
   to workload start. Small change to `run_static`/`run_sequential` plus a
   record schema bump.
2. **Decode slot utilization + prefill padding utilization** as first-class
   metrics. These state CB's predicted win (5.1x / 5.4x / 1.0x) *before* it's
   written.
3. **Warmup pass + `--repeat`** with median and spread.

### As part of the CB work, not before it

Refactor to a `step()`-shaped scheduler, then add the arrival-driven driver
(`--request-rate`, `--burstiness`). Static batching becomes the "wave scheduler"
behind the same interface — which is what makes the comparison one-variable per
rule 1, and it means the online harness lands on top of a refactor already being
paid for rather than on top of an engine about to be thrown away.

### After

λ sweep to the saturation knee, p50/p99 TTFT and TPOT, and **goodput under SLO**
(requests/s meeting e.g. TTFT < 200 ms ∧ TPOT < 50 ms). That last one is the
headline CB actually earns — static batching can't hold an SLO under load at any
batch size — and it's the number raw `tok/s` will never show.

### Later, for features already on the roadmap

A **shared-prefix workload**. Random token ids (`benchmarks/workloads.py:56`)
guarantee zero prefix sharing by construction, so when prefix caching lands
there will be no workload capable of showing it — and no "before" number. The
same limitation rules out anything else content-dependent (speculative decoding
acceptance rates, cache hit rates).

## Framing

The offline harness measures **capacity** (μ, the service rate). The online
harness measures **behavior under load**. μ has to come first, which is why the
current order was right — but μ is also the input to every queueing claim about
to be made, so it doesn't get retired.
